# Password recovery

On the sign-in screen, choose the account's original college and click **Forgot password?**. Enter the registered email, confirm the college and click **Send reset link**. Open the email, enter and confirm a new password, then click **Save new password**. Sign in again through the appropriate portal with the same college. The previously nominated administrator email is kamnaa313@gmail.com; its legacy account used Demo College 1. Selecting real college code 219 does not migrate that account or create administrator rights.

Recovery uses the existing configured Gmail API or Resend adapter. API-key presence does not establish successful inbox delivery. The default Resend sender is restricted to the configured owner's test inbox; other recipients require a verified sending domain. Gmail needs valid OAuth credentials. The API always returns the same request acknowledgement for known, unknown and unconfigured addresses. The account holder must confirm receipt; the service does not claim an email arrived merely because the provider accepted it.

Links expire after 30 minutes, are single-use, and replacement requests invalidate earlier links when delivery is configured. SHA-256 token digests are stored; raw tokens appear only in the emailed URL fragment and transient application memory. The frontend removes the fragment from the address bar and does not submit a reset until the user explicitly saves a password. Passwords remain bcrypt hashes, require at least 10 characters and permit at most 72 UTF-8 bytes. Password reset increments users.token_version: previous JWT sessions fail subsequent database-backed authentication. Legacy JWTs without that claim count as version zero until a reset. Roles, college membership, email verification and access approvals are preserved.

The password_reset_tokens table includes college_id, a composite tenant/user foreign key, ENABLE/FORCE college_isolation RLS, and explicit application college filters. Unknown requests store an HMAC request-address key, not a plain email. Transaction locks serialize issuance and completion. Database-backed limits are one request per minute and three per hour per address, plus sixty per hour per college. These limits can temporarily prevent legitimate requests when a college quota is exhausted; this is not a general login/signup rate limiter. Expired attempt retention and cleanup are not implemented yet.

Mail sending is best-effort background work after the transaction commits, not a durable queue. A process restart can interrupt delivery; provider acceptance is not inbox delivery. Failed/ambiguous sends are not automatically retried. A new request after the cooldown can replace the link. Password recovery is not a workaround for lost access to the registered mailbox or missing administrator authorization. No plaintext passwords or reset links should be shared in chat, logs or support tickets.

Local integration tests use disposable accounts and mocked email transport. Actual administrator inbox receipt and a user-completed live password reset remain acceptance checks until explicitly confirmed.
